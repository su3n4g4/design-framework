# 品質リスク分析

---

## 1. 目的

後続の論理設計・見積もり・アーキテクチャ方針に影響する品質特性（非機能要件）を、定量ではなく「リスク・傾向」として早めに拾う。

負荷が発生し得る箇所、失敗に弱い箇所、外部依存を抱える箇所を特定する。

---

## 2. 必要な情報

- 要件（特に運用の条件）
- ユースケース
- 概念モデル
- 責務割り当て（入出力／制御ロジック／データモデルの一覧、B→C→E 依存図、事後条件のEntity単位変換表）

---

## 3. 手順

毎回ゼロから考えないために、次の順番で進める。「何を重視するか」と「どこで制御するか」は別の軸として判断する。同時に考えると迷いやすいため、必ず優先度 → 制御場所の順で決める。

1. **候補を拾う**：下の「抽出チェックリスト」と「責務割り当ての成果物から拾う」で候補を洗い出す
2. **優先度を決める**：失敗したときの被害で決める
3. **制御場所を決める**：リスクの原因で決める
4. **品質リスク表に記録する**
5. traceability-check に従い、全行に抽出元があるか確かめる
6. 完了条件を確かめる

### 抽出チェックリスト

各品質項目について、3つの視点（UC／概念／B・C・E）から該当するか順番にチェックする。該当したものだけ品質リスク表に記録する。

**性能**
- [UC] 一覧・検索・集計など、データ量に比例して遅くなる操作があるか
- [UC] 同時実行されやすい操作があるか（例：セール開始時の購入）
- [概念] レコード数が増え続ける概念があるか（履歴・ログ・通知）
- [概念] 集計・計算対象になる概念があるか（売上、ポイント残高）
- [B] アクセスが集中しやすい画面・APIがあるか
- [C] 複数の外部API/DBを直列で呼ぶ制御ロジックがあるか

**可用性**
- [UC] 失敗すると金銭的・業務的に重大な影響がある操作があるか
- [UC] 外部サービスに依存する操作があるか
- [C] 部分的失敗でも継続すべきフローがあるか（例：通知失敗しても注文は成立）
- [C] リトライ可能か／冪等性を担保する必要があるか

**整合性**
- [概念] 複数のEntityを同時更新する操作があるか（トランザクション境界）
- [概念] 同一Entityが複数操作から同時更新される可能性があるか（排他制御）
- [E] 状態遷移を持つEntityがあるか（不正遷移の防止が必要）
- [E] 計算結果を保持するカラムがあるか（合計金額等 → 再計算 vs キャッシュ）

**セキュリティ**
- [UC] 認証が必要な操作はどれか
- [UC] 権限によって操作可否が変わるものがあるか（認可）
- [B] 外部からの入力を受けるエンドポイントにCSRF/XSS対策が必要か
- [E] 個人情報・機密情報を持つEntityがあるか（暗号化・マスキング）

**運用性**
- [UC] 障害時に調査が必要になりそうな操作はどれか（ログ粒度）
- [C] 外部API呼び出しのレスポンスタイム・エラー率を監視すべきか
- [E] データの定期削除・アーカイブが必要な概念があるか

**拡張性**
- [概念] 将来的に種類・区分が増えそうな概念があるか（商品種別等）
- [B] APIバージョニングが必要になりそうか
- [E] テーブル構造が頻繁に変わりそうな概念があるか

**保守性**
- [C] 条件分岐が多く複雑化しやすい制御ロジックがあるか
- [E] 設定値・定数がハードコードされそうな箇所があるか
- [B] 外部仕様の変更に影響される画面・APIがあるか

### 責務割り当ての成果物から拾う

チェックリストに加えて、責務割り当ての成果物からも候補をほぼ機械的に拾える。

| 成果物 | 拾う条件 | 品質項目の候補 |
|---|---|---|
| 事後条件のEntity単位変換表 | 変化の種類が「更新」「状態遷移」「削除」 | 整合性 |
| 事後条件のEntity単位変換表 | 複数のユースケースから同じEntityが更新される | 整合性（排他制御） |
| B→C→E 依存図 | 外部サービスを呼ぶ制御ロジック | 可用性・性能 |
| B→C→E 依存図 | 1つの制御ロジックから複数のデータモデルを更新 | 整合性（トランザクション境界） |
| 入出力の一覧 | 一覧・検索を返す入出力 | 性能 |
| 入出力の一覧 | ログイン状態や権限で結果が変わる入出力 | セキュリティ |

### 優先度を決める（失敗したときの被害で決める）

拾った候補ごとに、次の3つを上から順に問う。

1. **失敗したら取り返せるか**：決済・在庫・ポイントなど、不可逆な状態変化 → **高**
2. **影響は誰に及ぶか**：全体に波及する → **高**／1ユーザーで済む → **中**
3. **時間とともに悪化するか**：履歴・ログなど、データが増えると問題になるもの → **中**

どれにも当てはまらないものは **低** とする。

性能は気になりやすいが、多くの場合 3 に該当する。最初に悩むべきは「取り返せない状態変化」がどこにあるか。

### 制御場所を決める（リスクの原因で決める）

品質項目ではなく、**リスクの原因**から制御場所を決める。

| 原因 | 主な品質項目 | 制御場所 | 制御内容の例 |
|---|---|---|---|
| 入力が不正 | セキュリティ | 入出力 | 認可・CSRF・形式バリデーション |
| 手順が途中で失敗する | 可用性 | 制御ロジック | タイムアウト・再試行・フォールバック |
| 状態が矛盾する | 整合性 | データモデル＋DB | 不変条件・排他・一意制約・外部キー |
| 量が増える | 性能・拡張性 | データアクセス・インフラ | ページング・インデックス・キャッシュ |
| 起きたことが見えない | 運用性 | 横断 | ログ粒度・監視・アラート |
| 変更が波及する | 保守性 | 責務分割 | 設定の集約・依存方向の整理 |

**トランザクションの扱い**
- 境界（どこからどこまでを1つにするか）を決めるのは **制御ロジック**
- 矛盾しないことを保証するのは **データモデルとDB**

制御ロジックに整合性のルールそのものを書かない。制御ロジックは「この範囲をまとめて成功／失敗させる」ことだけを担う。

## 4. 出力フォーマット

「抽出元」列は必須。どこから拾ったリスクかを追えるようにする。定量目標（○秒以内など）はこの段階では書かない。リスクの所在と方針の方向性を揃えることが目的。

```markdown
## 品質リスク表

| # | 抽出元 | 品質項目 | リスク内容 | 優先度 | 制御場所 | 対応方針 | 備考 |
|---|---|---|---|---|---|---|---|
| 1 | UC-03（検索） | 性能 | データ量増加で応答遅延 | 中 | データアクセス | ページング必須、全件取得禁止 | |
| 2 | E:在庫 | 整合性 | 同時更新で数量不整合 | 高 | データモデル＋DB | 楽観ロック or SELECT FOR UPDATE | |
| 3 | C:購入処理 | 可用性 | 決済API失敗時の注文状態 | 高 | 制御ロジック | 冪等キーで再試行可能に | |
| 4 | B:トップ画面 | 性能 | アクセス集中 | 中 | インフラ | CDN/キャッシュ検討 | |
```

- 優先度：高／中／低（「優先度を決める」の3つの問いで判断）
- 制御場所：入出力／制御ロジック／データモデル＋DB／データアクセス・インフラ／横断／責務分割（「制御場所を決める」の表で判断）
- 抽出元の記法は id-notation に従う
- 「備考」列は空欄のままでよい。レビュー時に担当の割り振りや追加検討の起点として使う

## 5. 品質評価基準

### OKの基準（すべて満たすこと）

| 基準ID | 基準 |
|---|---|
| QR-01 | 品質リスク表の全行に抽出元が記載されている |
| QR-02 | 品質リスク表の全行に優先度と制御場所が記載されている |
| QR-03 | 事後条件のEntity単位変換表の「更新」「状態遷移」「削除」の行が、整合性リスクとして検討されている |
| QR-04 | ユースケースごとに性能・可用性・セキュリティのいずれかの観点でリスクが挙げられている |
| QR-05 | 「数値目標」ではなく「リスクの傾向・方針」として記述されている |
| QR-06 | 外部サービス依存があるユースケースに対して、失敗時の方針が書かれている |
| QR-07 | 更新頻度の高いデータモデルに対して整合性リスクが記載されている |

### よくある不十分パターン

- 「性能要件：3秒以内」のような数値目標だけになっている（QR-05）
- 外部API依存があるのにタイムアウト・再試行の方針が書かれていない（QR-06）
- セキュリティ観点（認可・CSRF・入力検証）が全て抜けている（QR-04）
- 抽出元が空欄、または記法ルールに沿っていない（QR-01）
- 整合性のリスクの制御場所が「制御ロジック」になっている（ルールはデータモデルとDB、制御ロジックはトランザクション境界のみ）（QR-02）
- 性能のリスクばかり「高」になっていて、取り返せない状態変化が見落とされている（QR-02）

---

## 6. 完了条件

- 抽出チェックリストのすべての項目を確認している
- 責務割り当ての成果物から拾える候補を確認している
- 品質評価基準 QR-01〜QR-07 を満たしている

---

## 7. AIに任せない判断の例

| 場面 | 該当する領域 |
|---|---|
| 性能や可用性の目標値（○秒以内、稼働率など）を決めたくなった | 品質リスクへの目標値 |
| 運用の条件から読み取れない負荷や利用状況を想定したくなった | 要件の解釈が割れる |
| 責務割り当てに誤りや不足を見つけた | 前工程の成果物の変更（差し戻し提案） |
