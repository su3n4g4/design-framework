# 入出力設計

---

## 1. 目的

UI や外部からの入力・出力の形を固定し、制御ロジックに引き渡せる形に整える。UI や外部仕様の変更が、この成果物だけで見えるようにする。

入力バリデーションは、クライアントの入力が正しいかを確かめるもので、データモデルとは責務を分ける。

- 型・必須・最小/最大などの形式的ルールだけを書く
- エラーメッセージは UI 上で分かる程度に書く
- 業務ルール（在庫など）は入出力側に書かない
- CSRF／認可／セッション確認なども、ここで整理する

---

## 2. 必要な情報

- ユースケース（アクター・トリガー）
- 責務割り当て（入出力の一覧、シナリオ担当の振り分け）
- 品質リスク表（制御場所が「入出力」の行。認可・CSRF・形式バリデーションなど）
- 制御ロジック（クラスとメソッド）

---

## 3. 手順

1. 責務割り当ての入出力ごとに、エンドポイント／画面と Controller のメソッドを決める
2. Request のパラメータを型と必須／任意で定義する
3. Response の構造を、返すべきフィールドに絞って定義する
4. 形式的な入力バリデーションを書く。品質リスク表で制御場所が「入出力」の行を反映する
5. Request から制御ロジックへの受け渡しを書く
6. 完了条件を確かめる

---

## 4. 出力フォーマット

```markdown
### 入出力

#### エンドポイント／画面
- ［URL or View名］ → ［Controller@メソッド］

#### 入力（Request）
- ［param: type, 必須/任意］

#### 出力（Response / ViewData）
- ［field: type］

#### 入力バリデーション（入出力側）
- ［param: 形式ルール］
- CSRFチェック: ［必須/不要］

#### Request → 制御ロジックマッピング
- ［Controller@メソッド］
  - ［引数］ ← ［取得元］
  - 呼び出し: ［制御ロジッククラス.メソッド(引数)］
```

記入例：

```markdown
#### 入力バリデーション（入出力側）
- quantity: int, min=1
- item_id: int, required
- CSRFチェック: 必須

#### Request → 制御ロジックマッピング
- GachaController@draw
  - userId ← セッションの user.id
  - gachaId ← request.gacha_id
  - quantity ← request.quantity
  - 呼び出し: GachaExecuteService.run(userId, gachaId, quantity)
```

---

## 5. 品質評価基準

### OKの基準（すべて満たすこと）

| 基準ID | 基準 |
|---|---|
| IO-01 | エンドポイントと Controller メソッドの紐づきが書かれている |
| IO-02 | Request パラメータが型と必須/任意で定義されている |
| IO-03 | Response の構造が実装レベルで書かれている |
| IO-04 | バリデーションが形式チェックのみ（業務ルールが混入していない） |
| IO-05 | Controller から制御ロジックへのマッピングが1行で分かる |

### よくある不十分パターン

- バリデーションに「在庫が十分であること」などの業務ルールが書かれている（IO-04）
- Response が Entity 丸ごとになっていて、返すべきフィールドが絞られていない（IO-03）

---

## 6. 完了条件

- 責務割り当てのすべての入出力が定義されている
- 品質リスク表で制御場所が「入出力」の行が反映されている
- 品質評価基準 IO-01〜IO-05 を満たしている

---

## 7. AIに任せない判断の例

| 場面 | 該当する領域 |
|---|---|
| 権限ごとの操作可否が要件から読み取れない | 要件の解釈が割れる |
| 入力の最大値・最小値など、形式ルールの値が要件にない | 要件の解釈が割れる |
| 責務割り当てにない画面やエンドポイントを足したくなった | 前工程の成果物の変更（差し戻し提案） |
