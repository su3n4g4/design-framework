# requirements-definition（0 要件定義）

- スキルの検証: 試運転1件完了（個人学習・技術知識管理システム Phase 1、Q27〜Q47）。独立した検証役での確認は未実施
- 位置づけ: 1-1 ユースケース定義より前。出力は設計ループの入力（要件）になる

## 1. 目的

利用者との質疑で要件を1論点ずつ確定させ、決定・提案・未決定を混ぜずに記録する。

**決めるのは常に人。** AIの仕事は次の2つに限る。

- 論点を整理し、選択肢と提案を用意する
- 回答を記録し、記録が正しいかを検証する

## 2. 入力

案件フォルダの中の置き場所：

| ファイル | 役割 |
|---|---|
| `requirements.md` | 要件定義書。要求・状態・版・変更履歴・再開ポイント。設計ループ（1-1 以降）の入力になる |
| `requirements/STATE.md` | 現在地、次の論点、検証結果の要約 |
| `requirements/decision_register.csv` | 決定台帳。回答で確定した決定（D番号） |
| `requirements/open_issues.md` | 未決定事項。論点の優先順 |
| `requirements/reviews/` | 検証レポート |

## 3. 手順（1反復＝1論点）

1. **論点を選ぶ**：STATE.md と未決定事項から、優先度と依存関係で次の1論点を選ぶ
2. **質問カードを作る**：§4の形式で作る
3. **検証する（質問時）**：検証役が RQ-01、RQ-09、RQ-10、RQ-12 を確認する
4. **一時停止**：質問カードを提示し、回答を待つ（承認ポイント）
5. **記録する**：回答を受けて次の4つを更新する
   - 決定台帳：D番号を連番で追加
   - 要件定義書：要求・状態・版・変更履歴・再開ポイント
   - 未決定事項：回答済みの論点を移し、新しく出た論点を追加
   - STATE.md：現在地と次の論点
6. **検証する（記録時）**：
   - 機械検証：設計フレームワークの `scripts/check-requirements.py` に案件フォルダを渡して実行（場所は入口 requirements-loop に書かれている）
   - 意味検証：検証役が RQ-02〜RQ-08、RQ-11 を確認
   - レポートは `requirements/reviews/` に保存し、`requirements/STATE.md` には要約だけ書く
7. **直す**：BLOCKER／MAJOR があれば作る役が直して6に戻る
   - 上限は3回。同じ指摘が2回続いたら人に判断を求めて止まる
8. 次の反復へ

## 4. 出力フォーマット：質問カード

```
## Qnn：<論点>

背景：関連する決定（D-xx）と要求（R-xx）
選択肢：A／B／C（それぞれの長所・短所・影響する要求）
提案（未決定）：推す選択肢と理由
回答方法：A／B／C、または調整内容
```

## 5. 品質評価基準

| ID | 基準 | 重大度 | 確認時期 | 方法 |
|---|---|---|---|---|
| RQ-01 | 1回に1論点だけ聞いている | MAJOR | 質問時 | 意味 |
| RQ-02 | 回答で選ばれていない提案を、決定として記録していない | BLOCKER | 記録時 | 意味 |
| RQ-03 | 既存の決定を無断で変えていない。変えるのは回答で明示された場合だけで、変更履歴が残っている | BLOCKER | 記録時 | 意味 |
| RQ-04 | D番号が連番で、重複も欠番もない | MAJOR | 記録時 | 機械 |
| RQ-05 | D-88以降の決定が要件定義書から参照されている | MAJOR | 記録時 | 機械 |
| RQ-06 | 状態の表記が定義済みの語を使っている | MINOR | 記録時 | 機械 |
| RQ-07 | 3つのファイルで「最終回答」と「次の質問」が一致している | MAJOR | 記録時 | 機械 |
| RQ-08 | 利用者申告の参考情報や前提を、要求・決定と区別している | MAJOR | 記録時 | 意味 |
| RQ-09 | 選択肢が既存の決定と矛盾しない。矛盾する場合はそれを明記している | MAJOR | 質問時 | 意味 |
| RQ-10 | 提案に「未決定」と明記している | MINOR | 質問時 | 意味 |
| RQ-11 | 版と変更履歴を更新している | MINOR | 記録時 | 意味 |
| RQ-12 | 選択肢や新しい項目が、後のフェーズの範囲を現フェーズに持ち込んでいない | MAJOR | 質問時 | 意味 |

状態の語：確定／確定（詳細未定）／基本方針確定／候補／未決定／保留（「Phase 1範囲確定」など、Phase名を前に付けた形も可）

指摘には、根拠となるファイルと該当箇所の引用を必ず付ける。

## 6. 完了条件

- 対象フェーズの「高」優先の論点がすべて回答済み、または利用者が保留と決めている
- 受け入れ条件（AC）が利用者に承認されている
- 最後の記録時検証で BLOCKER／MAJOR がない

## 7. AIに任せない判断の例

| 場面 | 扱い |
|---|---|
| 回答が「C」だけで、提案した細部まで同意したか分からない | 選択肢だけを決定として記録し、細部は未決定に残す |
| 回答が既存の決定と矛盾する | 記録せず、どちらを優先するか確認する |
| 既存の決定を変える選択肢がある | 質問カードに「D-xxを変える」と明記する。選ばれたら台帳の旧行は書き換えず、新しいD番号で変更を記録し、要件定義書の変更履歴に「既存決定の変更」と書く |
| 決定済みの論点を見直す | 新しいQ番号を振り、元の決定を変える選択肢として質問カードを作る |
| 利用者の疑問や提案を受けて選択肢を作り直す | 元の選択肢との違いを明示し、回答が確定するまで何も記録しない |
| 論点の優先順を変えたくなった | 理由を添えて提案し、人が決める |
| 回答から新しい要求を思いついた | 未決定事項に「提案」として追加するだけにする |
