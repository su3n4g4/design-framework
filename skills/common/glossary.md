# 用語

設計フレームワークの全フェーズで、用語はこの定義に従う。新しい用語を定義したり、意味を変えたりする場合はAIだけで決めず、人間に確認する。

---

## 処理ブロック

| 用語 | 定義 |
|---|---|
| 入出力（Boundary） | ユーザーや外部からの入力を受け取り、結果を返す部分。画面・API・フォームなど外界との境界 |
| 制御ロジック（Control） | ユースケースの流れを進める司令塔。複数のデータモデルを呼び出すが、自身はビジネスルールを持たない |
| データモデル（Entity） | 自分自身の状態・データ・ビジネスルールを持つ。状態変化や計算など内側のロジックを担当する |

**注意**：このフレームワークの「データモデル」は Entity の日本語表記で、クラスとしての設計を指す。一般に言う DB の設計（ER 図など）ではない。DB の設計は「テーブル設計」と呼ぶ。

説明文では日本語の名称（入出力／制御ロジック／データモデル）を使う。B／C／E の略記はテンプレート・表・コードブロックの中だけで使う。

---

## 設計の要素

| 用語 | 定義 |
|---|---|
| ユースケース | 外から見た動き。アクター・目的・主シナリオ・代替シナリオ・事前条件・事後条件で構成する |
| アクター | ユースケースを始める人、または外部のもの |
| 主シナリオ | ユースケースが目的を達成する、標準の流れ |
| 代替シナリオ | 主シナリオから分岐する別の流れ。エラー条件による分岐を含む（1-1 で扱う） |
| 事前条件 | ユースケースの開始時に満たされている状態 |
| 事後条件 | ユースケースの終了時に保証される状態 |
| 概念モデル | モデル化の対象になる名詞（概念）と、その関係。後のデータモデルやテーブルへの橋渡しになる |
| 責務割り当て | ユースケースの各ステップを入出力／制御ロジック／データモデルに分類すること。一般にはロバストネス分析と呼ばれる |
| 品質リスク | 性能・整合性・外部依存など、機能は満たしても品質を損なうおそれ |
| 例外フロー | エラーや異常時の扱い。入出力とデータモデルのどちらが担当するかを決める（5 で扱う） |
| DAO | テーブルへの読み書き（select／insert／update など）を担うクラス。見積もりではテーブル数とほぼ同数と見込む |
| DTO | 層の間でデータを受け渡すための入れ物。制御ロジックが結果を入出力に返すときなどに使う |

## 設計ループ

| 用語 | 定義 |
|---|---|
| 設計フレームワーク | 設計の「やり方」の定義。このリポジトリ全体を指す |
| 案件 | 設計フレームワークを使って設計する個々の対象。案件ごとに成果物と状態を持つ |
| フェーズ | 設計の工程の単位。1フェーズ＝1ループ＝1スキル |
| スキル | 1つのフェーズ、または共通の作業の手順と基準をまとめたもの |
| 実装者 | スキルに従って成果物を作る役（AI） |
| 検証役 | 実装者とは別の文脈で成果物を検証し、承認か却下かを判定する役（AI） |
| 承認ポイント | 人間が成果物を確認し、次へ進めるか差し戻すかを判断する地点 |
| 確認待ち | AIが人間の判断を必要として止まっている事項 |
| 差し戻し | 前のフェーズに戻って成果物を作り直すこと。人間が決める |
